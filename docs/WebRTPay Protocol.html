WebRTPay Protocol
Protocol · webrtpay/1

Paying wallet to wallet, directly

WebRTPay lets two BSV wallets open an encrypted WebRTC connection and hand a payment straight from one to the other. Servers help the wallets find each other; the payment itself never passes through them.

Architecture

Two wallets, a direct channel, and a few helpers

Everything that matters happens between the two wallets. The helpers in the middle each do one narrow job, and none of them is trusted with the payment or the signalling contents.

Payer

Sending wallet

Looks the payee up by identity key, dials, proves who it is, then sends a PeerPay payment token and waits for the acknowledgement.

Signalling carrier

Relay, message box or QR code

Carries a handful of small, end-to-end encrypted envelopes so the wallets can agree how to connect. Sees who signals whom, never what.

Address discovery

STUN servers

Each wallet asks “what is my public address?” so it can be reached through home routers. One packet, no payment data.

Fallback only

TURN server

Forwards already-encrypted packets when two networks cannot connect directly. Cannot read them.

Payee

Receiving wallet

Answers while its app is open, checks the payer’s identity, verifies the transaction, adds it to the wallet and acknowledges.

Direct WebRTC data channel DTLS 1.2+ encrypted, one ordered reliable channel named webrtpay/1. The identity handshake and the payment travel only here.

Finding each other

Three ways to start a connection

The direct channel is the same in every case. What changes is who helps the two wallets swap their connection details, and so what that helper could learn.

No carrier at all

Face to face: webrtpay1: codes

The payee shows an offer code as a QR; the payer scans it and shows an answer code back. No server learns that these two wallets met. Anyone who can photograph the codes sees the candidate addresses inside them, and the offer names the payee’s key; the answer code carries no key.

Sees metadata

Relay server

A stateless WebSocket rendezvous. Each wallet signs in with its identity key, and the relay forwards encrypted envelopes to whichever sockets hold the recipient’s key. It stores nothing and never logs payloads, but it does see both keys, both IP addresses and the timing of every signal.

Sees and stores metadata

Message box

The envelope travels as a message in the webrtpay_signals box. Same visibility as the relay, plus the encrypted message is held on the server until the recipient reads and acknowledges it, usually within a second or two.

In plain terms

What stays private, and what does not

Private between the two wallets

  • The payment token, the amount, the note and the acknowledgement. They travel only inside the DTLS channel.
  • Every knock, ring, offer, answer and refusal. Each is encrypted to the recipient’s identity key, so a carrier only forwards ciphertext.
  • Who you really are to the other side. Identities are proved with signatures bound to this exact connection, so nobody in between can stand in for either wallet.
  • The link between the payment on chain and your identity. Each payment output uses a fresh key derived for that one payment.

Visible to the carrier for that dial

  • That identity A contacted identity B, at what time, and how often. This is enough to build a contact graph of who pays whom.
  • The IP address of each connected wallet, and therefore a rough location.
  • Whether a given identity is online right now. The relay’s offline reply and the payee’s ring both reveal it.
  • With TURN in use, the TURN provider sees which two addresses are talking, though not who they are.
So is it untraceable?

Not when a carrier is involved. A third party never learns what was paid or what was said, but the relay or message box operator can see that two identities connected, when, and from where. If they kept that record, it could be used to trace who pays whom. The relay is built to keep nothing (it stores no messages and logs no payloads), but that is a policy of whoever runs it, not something the protocol can prove. Face-to-face codes avoid carriers entirely.

Receiving

What being open to payments reveals

BSV Desktop now receives live payments by default while the app is open. That is convenient, and it has a cost the person should know about:

Your online status

Anyone who knows your identity key can knock and learn from the ring that your wallet is open, without paying. Rings are capped at 20 a second, and knocks count against the intake limits.

Your public IP address

Anyone who knows your key can send an offer and get an answer containing your public address, again without paying. No address is gathered for a knock or for a refused offer. Local network addresses are hidden behind random mDNS names.

The payer’s address, to you

Dialling reveals the payer’s public address to the payee. Payment is a two-way conversation, so each side learns the other’s address.

The off switch

Live receiving can be turned off in Settings. Payments then wait in the message box and are added automatically the next time the app opens.

Security properties

Why a payment cannot be redirected or replayed

Channel binding

Each side signs a transcript of both DTLS certificate fingerprints, both 32-byte nonces and both identity keys under protocol [2, 'webrtpay channel']. A man in the middle terminates DTLS separately with each side, so the fingerprints differ and neither signature verifies.

Encrypted, addressed signals

Every envelope is BRC-2 encrypted under [2, 'webrtpay signaling'] with the session id as key ID. The receiver checks that the sender inside matches the sender the carrier claims, and that the envelope is addressed to it.

Replay protection

A signal must be within 120 seconds of the receiver’s clock, and each session id is accepted once per kind and remembered for three minutes, longer than that window, so a captured signal cannot be sent again.

Checked before acknowledged

The payee verifies the transaction and the output’s amount before it acknowledges. The payer checks the token the same way before it broadcasts, so a payment the payee would refuse is never spent.

Bounded intake

Per-sender and global limits on knocks, offers, sessions and message sizes. A sender over its limits gets no reply at all, so it cannot spend the refusal budget either.

Network-bound dials

Offers, answers, knocks and rings name the network. A mainnet wallet refuses a testnet peer before any address is exchanged.

Reducing what carriers learn

Options, strongest first

  1. Use face-to-face codes when you are in the same place. No carrier is involved, so no server sees who paid whom.
  2. Run your own relay. The relay is open source (webrtpay-relay) and stateless. A community or business that runs its own sees only its own members’ metadata.
  3. Prefer direct connections. TURN is a fallback for networks that block peer-to-peer; when it is not needed, no forwarding service sees both addresses.
  4. Turn live receiving off if your online status and IP address matter more than instant payments. Message box payments still arrive.
